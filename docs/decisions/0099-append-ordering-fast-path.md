# ADR-0099: unchanged-prefix array ordering

Status: Experiment (16k); no measured application win yet.

The hash-verified 16j3 append diagnostic executes one native batch per action. Source investigation identifies avoidable JS work before that batch: matchElements builds an identity bucket for every old element even for an unchanged prefix, and reorderedPositions computes LIS for a pure append. Root caching for onState reset is deferred: merging roots into PathCache absorbs descendant leases and can retain unselected state; a separate cache would add retention and invalidation complexity.

Decision: consume the identical prefix before building remaining identity buckets (SameValueZero equality, preserve sparse arrays). For an exact old-index prefix followed only by unmatched items, retain old positions and append consecutive positions, applying the existing renormalization check. Reorders, insertions and non-prefix matches retain the existing LIS path. No SQL, schema, row cap, notification or public API changes.

Plan: (1) allocation/work regression tests must fail first; (2) compare seeded duplicate/sparse/NaN/reorder cases against the existing matching/position algorithm; (3) implement minimal fast paths; (4) all library tests, then build candidate and reversed append diagnostics with hash/sample provenance; (5) 50k list A/B against 15aa; (6) retain only measured benefit or proven redundant work removed, with full list acceptance required before closure. No git commit. Acceptance reports and frozen 16j baseline remain intact.
