# ADR-0105: asynchronous burst backlog has a positive lower bound

Status: Evidenced limit for the zero-parity target only. No new acceptance floor or report reclassification.

Scope: Phase16flat50/500/5000 burst.maxBacklog. The verified retained16r protocol and current16u both dispatch90 distinct writes at30Hz for3seconds,with90observed values in every trial. ClassicmaxBacklog is0inall15trials per build;16rSQLitebacklogs are2/2/2/2/2 atK50,3/3/3/2/2 atK500,and2/2/2/2/2 atK5000.16uSQLitevaluesare3/3/2/2/2,2/2/2/3/2,and2/2/2/2/2 respectively. Fullsha-linkedrawproof is android-burst-backlog-limit-2026-10-28.json.16uisprovisional;the architectural proof and retained16r evidence do not depend on retaining it.

Proof: shapes-hook.flatBurst calls store.dispatch, increments i,then reads lastSeen and records i-1-lastSeen in the sameJavaScript call stack. On the firstdispatch,i becomes1. ClassicNgRx delivers the reducer state synchronously,so lastSeen=0andbacklog=0. SQLite's dispatch returns synchronously but nativecommit and post-commit selector emission are asynchronous(ADR0003). No nativePromise callback can execute before the currentJavaScript stack yields. Thus lastSeen=-1andbacklog=1atthat checkpoint,even if the eventual native service time approacheszero. Maximumbacklog istherefore>=1forany correct asynchronousSQLiteimplementation of this workload.

Achieving0would require notify-before-commit, changing synchronousdispatch/the workload's observation point,or synchronouslyblockingthemainthreaduntilanasyncnativecallbackruns. The first violates persistence/notification guarantees,the second changes the measured contract,and the third cannot deliver the queuedJavaScript callback while blocked. Skipping/coalescing observable actions also violates the required history. There is no such implementation change authorized here.

This is an evidenced architectural limit on matching classic0,as allowed by the user's Phase16goal. It does NOT prove observed2-3 isoptimal,does NOT excuse excess latency,unboundedqueuegrowth or lostobservations,and does NOTresolveanyothermetric. Queueheadroomabove1remains a valid optimization target. Hook summaries lack per-action service/queue times,so no measured upperbound is invented. Existing PASS/PB/FAIL report rows remain unchanged;no backlogfloor is applied and no floor approval is requested.
